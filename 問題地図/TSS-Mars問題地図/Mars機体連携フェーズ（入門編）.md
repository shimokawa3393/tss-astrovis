## 0. このフェーズの問い

**「ドローンをOptimusの目にする」**

Optimusは自分のカメラで、目の前の数mを見られる。ドローンは、数百m先を上から見渡せる。

```
ドローン → 「この先の地形はこうなってる」
Optimus  → 「じゃあこのルートで行く」
```

この「地形の情報を渡す」設計が、Optimus連携の核心。

## 1. 地形データの形式と受け渡し

### なぜ点群をそのまま渡せないか

| 問題 | 中身 |
|---|---|
| 容量 | 1回の飛行で数百MB。そのままではリアルタイムに処理できない |
| 形式 | 座標の羅列なので、Optimusの行動計画エンジンが直接使えない |

### グリッドマップ(占有格子)に変換して渡す

```
点群(生データ)
    ↓ 処理
グリッドマップ(占有格子)
□□□□□□
□■■□□□   ■ = 岩(通れない)
□□□□■□   □ = 平地(通れる)
□□□□□□
```

### 解像度の使い分け(LOD)

人型ロボットの肩幅は約50〜60cm(想定)。2〜3mの格子では岩を見落とす。

| エリア | 格子の大きさ |
|---|---|
| 遠く(粗い) | 1〜2m |
| 近く(細かい) | 0.1〜0.5m |

RPGのフォグ・オブ・ウォーと同じ構造。未探索のところは霧で、近づくと詳しく見える。ドローンが飛ぶたびに霧が晴れていく。

## 2. Optimusの行動計画への統合

グリッドマップをもとに、Optimusが経路を計算する。

| アルゴリズム | 用途 | 特徴 |
|---|---|---|
| A* | 広い範囲のルート計画(グリッドマップで) | 速い。格子の上で最短経路が保証される |
| RRT | 足元の細かい障害物回避(3D点群で) | 複雑な形に強い |

## 3. リアルタイム更新の仕組み

### 通信フェーズの「先読み」と同じ構造の問題

```
ドローンがマップを作る(Optimusの位置: A地点)
        ↓ 処理と送信に約0.5秒
Optimusが受け取る(Optimusの位置: B地点)
```

マップはA地点を基準にしているが、Optimusはもうそこにいない。

### 解決: 予測補正

```
Optimusの現在位置と、移動速度・方向
        ↓
0.5秒後の位置を予測する
        ↓
その位置を基準にマップを補正して渡す
```

550AUのレーザー通信で、未来の地球の位置を狙うのと同じ発想。カーナビの位置補正とも似ている。

## 4. 機械どうしの送受信

### ローカル通信の使い分け

| 用途 | 通信方式 | 中身 |
|---|---|---|
| 小容量・低消費電力 | LoRa系 | コマンド・状態報告 |
| 大容量・広帯域 | Wi-Fi系 | グリッドマップ・点群 |

### 通信圏外の問題

ドローンが5km先まで飛ぶと、Wi-Fiの圏外になる。ローバーが中継器になることで解決する。

```
ドローン(5km先)
      ↓ Wi-Fi
ローバー(3km地点)
      ↓ Wi-Fi
Optimus(基地)
```

## 5. 統合OS(マルチエージェントOS)

### なぜ必要か

3者がばらばらに判断すると、連携が崩れる。

```
ドローンが「東に飛ぶ」と判断
ローバーが「西に移動」と判断
        ↓
通信圏外になりデータが途絶える
        ↓
Optimusが崖に向かって歩く
```

### 共有状態(Shared State)

3者が常に同じ世界を見ている状態を保つ。

```json
{
  "timestamp": "T",
  "drone":   { "pos": [1, 2, 10], "battery": 80 },
  "rover":   { "pos": [3, 4],     "battery": 65 },
  "optimus": { "pos": [5, 6],     "battery": 91 },
  "grid_map": "最新版",
  "status": "normal"
}
```

### ロールスイッチング

異常の種類に応じて、3者が役割を自動で組み替える。

| 状態 | ドローン | ローバー | Optimus |
|---|---|---|---|
| 正常時 | 偵察・マッピング | 充電ステーション・中継 | 行動・探索 |
| ドローン故障 | — | 捜索・回収へ | 中継の位置へ移動 |
| 通信断 | 最後に分かっている位置へ戻る | 中継器に昇格 | 手持ちのマップで自律行動 |
| 電池低下 | ローバーに自律着陸 | 充電する | 継続 |

1台が止まっても、残りが穴を埋めて全体が生き続ける設計。

## 6. 連携プロトコルのオープン化(OSS戦略)

### なぜOSSにするか

```
TSS-Mars統合OSをOSSで公開
        ↓
SpaceXのエンジニアがGitHubで見つける
        ↓
自分たちで作るより使う、と判断する
        ↓
TSS-Marsが業界標準になる
```

### APIとしてつなげてもらう

```
TSS-Mars統合OS(しもちが作る・OSS)
        ↓ API
Optimus OS(Teslaが作る)
```

こちらが仕様を先に作り、Tesla側がそれに合わせる。下請けではなく、業界標準を作る側に立つ。

**パクられるより、無視される方が怖い。** 先に標準を作った人間が主導権を持つ。

## TSS-550との差分まとめ

| 項目 | TSS-550 | TSS-Mars Optimus連携 |
|---|---|---|
| 通信相手 | 地球だけ | Optimus・ローバー・地球 |
| データ形式 | 画像・テレメトリ | グリッドマップ・点群・状態 |
| 遅延の問題 | 片道約76時間(光の遅延) | 約0.5秒(処理の遅延) |
| 冗長設計 | 探査機単体 | 3者のロールスイッチング |
| OSSの対象 | 画像再構成アルゴリズム | 統合OS・連携プロトコル |

## 一言まとめ

**ドローンは目。ローバーは足場。Optimusは手。統合OSが3者を1つのチームにする。**
