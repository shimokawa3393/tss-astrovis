## 0. なぜMarsの通信は550と根本から違うか  
  
TSS-550の通信の核心は、  
**「76時間遅延でどうやって届けるか」**  
だった。  
TSS-Marsの通信の核心は、  
**「繋がるタイミングを管理しながら、依存インフラが死んでも生き残るか」**  
になる。  
構造が違う。  
  
**TSS-550**  
```
探査機 ─────────────────────── 地球
         （2点間・常時接続・遅延あり）

```
**TSS-Mars**  
```
ドローン ─── 中継機（火星軌道） ─── 地球
  ↕                               （3点経由・断続接続）
Optimus
（ローカル通信）

```
ドローンは高度5〜12mで飛んでいる。  
地球との距離は最短5,500万km。  
直接通信は物理的に不可能。  
**中継機経由が強制される。**  
  
⸻  
  
## 1. 地球との長距離通信設計  
  
## 現状の火星中継ネットワーク  
NASAとESAが共同で運用する Mars Relay Network が、地球↔火星の通信インフラ。  

| 衛星                | 打ち上げ年 | 運用機関 | 状態            |
| ----------------- | ----- | ---- | ------------- |
| MAVEN             | 2013年 | NASA | 2026/6/3 死亡宣言 |
| MRO               | 2005年 | NASA | 運用中（21年目）     |
| Odyssey           | 2001年 | NASA | 運用中（25年目）     |
| Mars Express      | 2003年 | ESA  | 運用中           |
| Trace Gas Orbiter | 2016年 | ESA  | 運用中           |
  
MAVENは2025年12月6日が最後の交信。  
火星の裏側を通過した直後にスピン状態に陥り電力喪失。  
2026年6月3日に正式死亡宣言。  
MROとOdysseyは設計寿命を大幅に超えた老齢機。  
いつ突然死してもおかしくない。  
  
**TSS-Marsの2段階戦略**  
**Phase M-1〜M-3（前半）**  
NASA/ESAの既存軌道機を借りる。  
* MRO  
* Odyssey  
* Mars Express  
* Trace Gas Orbiter  
→ 今すぐ使える  
→ コストゼロ  
**Phase M-4〜（後半）**  
自前の中継CubeSatを打ち上げる。  
* Chapter 4のCubeSat技術を転用  
* 550本流と直結  
  
⸻  
  
## 2. コンタクトウィンドウ  
  
中継機は火星軌道を約2時間で一周する。  
ドローンの真上を通過する時間は、  
**1回約10分前後。**  
  
## 1日のタイムライン（イメージ）  
```
00:00 ─ ウィンドウ（約10分）通信可能 ─┐
00:10 ─ 通信不可（中継機が軌道の反対側）│
02:00 ─ ウィンドウ（約10分）通信可能  │ 繰り返し
02:10 ─ 通信不可                      │
...                                   └┘

```
1日のうち通信できる時間はせいぜい数十分。  
残りはボッチ。  
  
## データ量と帯域の現実  
MROの通信速度：  
**最大約2Mbps**  
```
2Mbps × 600秒（10分）
= 1,200Mb（メガビット）

÷ 8（1バイト = 8ビット）

= 150MB（メガバイト）

```
* 1フライトで取得する3D点群データ：数百MB  
* 1回のウィンドウで送れるデータ：約150MB  
→ 1回では送り切れない。  
  
**通信単位の整理**  

| 単位  | 表記      | 意味              |
| --- | ------- | --------------- |
| bps | 小文字b    | ビット（通信速度の単位）    |
| Bps | 大文字B    | バイト（ファイルサイズの単位） |
| 変換  | 1B = 8b | 必ず÷8が必要         |
  
  
⸻  
  
## 3. 遅延込みのコマンド設計（DTN）  
  
## MarsでDTNが必要な理由  
550のDTNは、  
**「76時間遅延でTCPのACKを待てない」**  
が理由だった。  
Marsは遅延が片道3〜22分（地球との距離で変わる）でも、中継機が軌道上を回っているため接続が物理的に途切れる。  
繋がる時間帯と、  
繋がらない時間帯が、  
交互にくる。  
これがMars固有の理由。  
  
## ストア＆フォワードの実態  
```
フライト終了
　↓
数百MBのデータをドローン内部に保存
　↓
ウィンドウ1回目（10分）
　→ 150MB送信
　↓
2時間待ち
（中継機が軌道の反対側）
　↓
ウィンドウ2回目（10分）
　→ 残り送信
　↓
全部揃ったら完了

```
##   
## エラー訂正  
途中のウィンドウでデータが壊れても破棄しない。  

| 手法           | 特徴                  |
| ------------ | ------------------- |
| Reed-Solomon | CDやDVDでも使われている古典的手法 |
| LDPC         | 現代の深宇宙通信の標準         |
  
冗長ビットを付加して送り、  
全部揃ったら壊れた部分を復元する。  
これは550通信フェーズ・環境耐性フェーズ（TMR）と同じ思想。  
壊れることを前提に、壊れても動く設計をする  
  
⸻  
  
## 4. Optimusへのデータ転送設計  
  
550にはない、  
完全Mars固有の通信相手。  
ドローンはOptimusの「目」になる。  
  
## 送信データの種類とサイズ感  

| データ種別      | サイズ感          | 優先度 |
| ---------- | ------------- | --- |
| コマンド・状態報告  | 数十バイト         | 高   |
| 異常検知結果     | 数KB           | 高   |
| カメラ映像      | 数MB/フレーム      | 中   |
| LiDAR 3D点群 | 数MB〜数十MB/フレーム | 中   |
  
**ローカル通信の構成**  
**近距離・小データ**  
* コマンド  
* 状態報告  
→ LoRa的な低消費電力通信  
**近距離・大データ**  
* 3D点群  
* 画像  
→ Wi-Fi的な広帯域通信（宇宙対応版）  
IngenuityはWi-Fi（802.11）ベースで、  
Perseveranceと最大1km通信していた実績がある。  
  
## 周波数制約について  

| 環境 | 状況                  |
| -- | ------------------- |
| 地球 | 電波法で周波数帯が割り当てられている  |
| 火星 | 電波法なし・混信を心配する相手もいない |
  
LoRaの433MHz自体は制約なく使える。  
ただし民生品のまま、  
* -60℃  
* 放射線  
には対応できない。  
宇宙対応版への変換が必要。  
→ 環境耐性フェーズで扱った設計思想が直結する。  
  
## メッシュネットワーク問題  
ドローンが5km先をマッピングするとWi-Fi圏外になる。  
```
ドローン（5km先）
　↓ Wi-Fi

Optimus A（3km地点）
　↓ Wi-Fi

Optimus B（1km地点）
　↓ Wi-Fi

基地局
　↓ 中継機経由

地球

```
Optimusが中継器になる。  
ストア＆フォワードと同じ思想。  
**繋がっている機械が橋渡しをする。**  
ただしOptimusの台数はTeslaとSpaceXの進捗に依存する。  
自分でコントロールできない。

## 5. 砂嵐時の通信途絶対策  
  
## 途絶の主因  
```
砂嵐
　↓
パネルに砂が積もる
　↓
発電ゼロ
　↓
電力がない
　↓
電波が出せない

```
電波が砂に遮られる効果もあるが、  
それより先に電源が落ちる。  
電力フェーズで扱った「突然死」が通信途絶の直接原因になる。  
  
## サバイバルモード中の通信優先順位  
```
優先度：高

ヒーター
（バッテリーを-15℃以上に保つ）

　↓

優先度：中

間欠送信
（まだ生きてます・位置はここ）

　↓

優先度：なし・全停止

観測データ送信
3D点群転送
Optimus連携
飛行

```
最優先は、  
**「動くこと」ではない。**  
**「次の晴天まで生き残ること」**  
である。

## 8. 差分まとめ  

| 項目     | TSS-550      | TSS-Mars          |
| ------ | ------------ | ----------------- |
| 通信構造   | 探査機↔地球（2点間）  | ドローン↔中継機↔地球（3点経由） |
| ローカル通信 | なし           | Optimus連携が必須      |
| 接続状態   | 常時（遅延はある）    | 断続的（ウィンドウ制約）      |
| 途絶原因   | 距離による減衰      | 砂嵐による電源喪失         |
| DTNの理由 | 76時間遅延でACK不可 | 中継機の軌道による接続断      |
| 依存構造   | 自前で完結        | 複数の外部インフラに依存      |
| 設計の自由度 | 高い           | 低い（外部インフラ前提）      |
  
  
⸻
